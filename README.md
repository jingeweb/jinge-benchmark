# Jinge / Vue / React 浏览器性能基准

此仓库以可重复运行的浏览器用例比较三套实现。README 由真实样本生成，先给出结果概要，再列出全部指标与用例；原始数据和测量代码随仓库保留。它是独立基准，列表操作参考 js-framework-benchmark 的场景，**不是该项目的官方实现或排行榜结果**。

## 各方向表现总结

**这轮实测中，Jinge 在包体和细粒度更新上有优势，但大列表更新和内存开销突出；Vue 比较均衡；React 在常规列表操作、批量更新和大列表内存上表现较好。**

以下均指本机、当前三套实现的结果。Vue 使用 JSX，React 使用不可变更新和 memo；耗时取中位数。定性解读针对本次实现与测量口径，修改用例、版本或配置后需要重新复核。

| 方向                       | Jinge                                   | Vue                        | React                                                           |
| -------------------------- | --------------------------------------- | -------------------------- | --------------------------------------------------------------- |
| 包体                       | 最小，JS 33.64 kB                       | 95.18 kB                   | 267.96 kB                                                       |
| 空页面启动                 | 最快，冷启动 ready 12.3 ms              | 15.6 ms                    | 26.9 ms                                                         |
| 带大量内容的启动           | 优势消失，千行表格冷启动 35.6 ms        | 千行表格最快，27.8 ms      | 32.4 ms；暖启动表格最快                                         |
| 列表创建、替换、追加、删除 | 多数场景较慢                            | 万行创建最快，交换行也突出 | 千行创建、替换、追加、删除较快                                  |
| 列表局部更新               | 明显短板：万行中更新千行为 **140.1 ms** | 5.2 ms                     | 4.1 ms                                                          |
| 大量绑定中只改一个         | 表现好，万绑定约 0.1 ms                 | 同样很好，约 0.1 ms        | 随组件数量增加，万绑定约 1.7 ms                                 |
| 同一轮批量更新             | 修改千属性为 4.4 ms                     | 2.5 ms                     | 最快，1.0 ms                                                    |
| 嵌套属性与对象替换         | 三者接近                                | 三者接近                   | 三者接近                                                        |
| 共享对象通知               | 千个别名更新为 4.4 ms                   | 1.9 ms                     | 1.0 ms                                                          |
| 挂载、卸载                 | 挂载较慢，卸载较快                      | 挂载接近 Jinge             | 挂载最快，卸载与 Jinge 接近                                     |
| 路由更新                   | 约 0.2～0.3 ms                          | 约 0.4～0.5 ms             | 约 15 ms，包含 React Router 默认调度等待                        |
| 表单输入                   | 三者都很快                              | 三者都很快                 | 三者都很快                                                      |
| 连续更新、滚动和拖动       | 小范围更新延迟低                        | 同样表现稳定               | 部分场景更新等待较长，但本次连续测试整体仍保持约 16.7 ms 帧间隔 |
| 大列表内存                 | 最高，万行总 JS 堆约 **69 MiB**         | 约 29 MiB                  | 最低，约 11 MiB                                                 |
| 重复挂载后的清理           | 堆持续增长值得重点排查                  | 增长较小，后期趋缓         | 增长较小，后期趋缓                                              |

路由的差距不能直接解释成 React 核心渲染慢几十倍，它包含各生态路由库的调度策略。布局和绘制本身也没有呈现统一的框架排名。

对三个框架分别看：

- **Jinge：小包、少量精准更新是强项。** 但当前精细订阅的成本在大量列表项、批量通知和对象保留上暴露出来。没有虚拟 DOM，并不意味着创建和更新大量 DOM 就一定更快。
- **Vue：这组用例中最均衡。** 单点更新快、大列表创建快，内存处于中间，没有类似 Jinge 万行局部更新那样突出的退化。
- **React：常规列表操作、批量更新和大列表内存表现突出。** 少量变化仍可能承担父组件遍历、不可变复制和调度成本；这些表现与具体组件拆分、memo 及路由配置有关。

**Jinge 下一步最值得排查的三个方向：**

1. **万行列表局部更新的 140.1 ms 开销**：通知传播、订阅遍历和子组件属性更新链。
2. **大列表的订阅内存成本**：为什么相同万行 DOM，JS 堆明显更大。
3. **重复挂载后的对象保留**：50 个子组件反复挂载卸载，10／50／100 轮后堆增量约为 0.48／1.90／3.65 MiB，持续增长；DOM 和监听器归零不能证明其他对象已释放。

## 结果概要

- 测量完成时间：2026-11-06T08:47:06.073Z。基于 npm 最新稳定版 React 19.3.1 / React DOM 19.3.1、Vue 3.5.45，以及 Jinge 4.2.1 / compiler 4.2.1。版本按本次测试日锁定，不随读者未来运行自动升级。
- 正确性：87 项浏览器场景通过，另有共享数据模型的可变/不可变更新一致性检查。覆盖列表 key 身份、路径/query 更新时页面复用、页面切换时替换，以及子组件挂载/卸载计数。
- 覆盖：29 项操作 × 3 框架；6 项启动场景 × 3；3 项连续更新 × 3；7 项内存场景 × 3。操作每项 5 次预热、30 次正式采样。
- 主基准应用 JS / gzip：Jinge 33.64 / 11.12 kB；Vue 95.18 / 35.85 kB；React 267.96 / 84.18 kB。包括主基准场景、路由和观测代码（滚动/拖动使用独立入口，不计入这里），并非最小 Hello World 或框架裸包。
- 本机这组实现中，Jinge 中位数明显较小的场景示例：query 变化，复用页面（Jinge 0.20 ms，Vue 0.40 ms，React 15.30 ms）；路径参数变化，复用页面（Jinge 0.30 ms，Vue 0.50 ms，React 15.10 ms）；切换页面，卸载并挂载（Jinge 0.30 ms，Vue 0.50 ms，React 15.20 ms）。
- 也存在 Jinge 中位数较大的场景：10000 行中每十行更新一行（Jinge 140.10 ms，Vue 5.20 ms，React 4.10 ms）；交换第 2 与第 999 行（Jinge 3.60 ms，Vue 0.80 ms，React 5.90 ms）；同一轮修改 1000 / 1,000 个属性（Jinge 4.40 ms，Vue 2.50 ms，React 1.00 ms）。这些结果一并保留，不能从包体小推断所有更新更快。
- 摘要只描述本机观测值，筛选示例的 20% 差距不是统计显著性检验。亚毫秒结果易受时钟粒度和调度影响，不给出跨场景总分或普遍速度倍数。

补充结果：真实滚动/拖动共 3 类 × 3 框架 × 3 轮已通过事件与最终状态校验，启动 CPU 另有 3 类 × 3 框架；补充采样完成于 2026-11-06T08:52:42.810Z。

内存方面，Jinge 的 mount-100 用例在 GC 后堆增量中位数为 3.65 MiB，DOM 与监听器增量均为 0 / 0；10、50、100 轮的增长明细在下方。它是需要进一步定位的保留增长信号，不用“节点已释放”代替堆内存分析，也不直接断言已经证明泄漏。

## 环境与实现口径

| 项目       | 本次配置                                                      |
| ---------- | ------------------------------------------------------------- |
| 硬件       | Apple M2，8 逻辑核，16 GiB 内存                               |
| 系统       | darwin 27.2.0 / arm64                                         |
| 浏览器     | Chrome 156.0.8078.80，headless，1280×900，DPR 1               |
| 工具       | Node v26.4.0，pnpm 12.16.1，Vite 8.3.6，Playwright 1.65.0     |
| CPU / 网络 | CPU 1×；本机 HTTP、无网络限速、实际传输不启用 gzip            |
| 路由       | jinge-router 4.2.0；vue-router 5.4.0；react-router-dom 7.18.5 |

三套应用使用相同的数据生成器、最终 DOM 结构、CSS、视口和固定尺寸布局，没有虚拟列表。Jinge 使用编译后的 TSX 与 VM；Vue 使用官方 JSX 插件与 reactive（不是 SFC 模板）；React 使用 createRoot、useState、结构共享的不可变更新及 memo 行/字段组件，未启用 StrictMode、React Compiler 或 flushSync。

这比较的是仓库中的具体实现与配置，不代表所有写法的最优上限，尤其不能把 Vue JSX 结果直接等同于优化过的 SFC 模板结果。可变对象更新与 React 不可变复制是各自实现的一部分，计时包含实际数据处理与调度；没有把 React 改造成外部信号订阅系统，也没有对代理框架强加深拷贝。

路由指标包含各自路由库及默认调度的成本；React Router 没有强制同步提交，不能把这组路由差异直接当作 React DOM 与 Jinge 核心的纯渲染差异。

各框架串行执行，不并行跑测量；主要操作和启动延迟按轮轮换框架顺序，诊断、连续更新、内存及手势按场景/框架串行执行。预置数据和准备 DOM 位于操作计时之外；创建/追加操作自身的数据创建仍位于计时之内。完整 DOM 结果在计时后核对。无关页面保持静止，关闭开发构建及 HMR。

## 复现与仓库结构

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm bench
pnpm report
```

默认使用本机 Chrome。没有安装 Chrome 时运行 `pnpm exec playwright install chrome`；或安装 Playwright Chromium，并设置 `PLAYWRIGHT_CHANNEL=chromium`。报告会记录实际浏览器版本。

完整测量默认操作 30 次、预热 5 次、启动 30 次、内存 3 次、连续更新 3 轮。环境变量 BENCH_SAMPLES、BENCH_WARMUP、BENCH_STARTUP_SAMPLES、BENCH_MEMORY_SAMPLES、BENCH_FRAME_TRIALS 可调整次数；BENCH_CPU=4 可另跑 CPU 降速配置，不能与默认结果混合。BENCH_ONLY=operations,startup,diagnostics,continuous,memory 可选择类别，部分运行仅输出 JSON，不生成完整 README。BENCH_TRACES=0 可关闭额外 trace。

- src/shared/model.ts：确定性数据、可变/结构共享不可变更新、正确性 oracle。
- src/shared/cases.ts：所有操作和连续场景参数。
- src/shared/bridge.ts：统一完成观察、事件记录和浏览器驱动接口。
- src/jinge、src/vue、src/react：三套界面与真实路由实现。
- scripts/verify.mjs：全场景结果、key 身份、页面复用及生命周期验证。
- scripts/run.mjs：串行、轮换顺序的采样、启动、CPU、内存与 trace。
- scripts/report.mjs：从完整结果生成本文，拒绝未完成或缺少类别的结果。
- [results/latest.json](results/latest.json)：逐样本原始数据、环境、统计及 trace 校验值。
- [results/verification.json](results/verification.json)：正确性验证记录。
- [results/artifacts.json](results/artifacts.json)：构建文件明细；kB=1000 bytes，gzip 为文件级离线压缩值。

### 堆快照定位

执行 `pnpm heap jinge`（也可传 vue / react），在独立上下文中保存 50 个子组件反复挂载前、100 轮卸载后的堆快照和摘要。快照可用 DevTools Memory 的 Comparison / Retainers 查看；.heapsnapshot 和大型 trace 不纳入 Git，JSON 摘要与校验值保留。当前已生成 Jinge 的快照及 results/jinge-heap-notes.json，方便继续定位上述增长；没有修改任何框架源码来改变本次结果。

扩展驱动为 scripts/extended.mjs，独立手势入口为 src/*-gestures，原始补充结果为 results/extended.json。BENCH_GESTURE_TRIALS 控制手势轮数；pnpm bench:extended 可以在完整主基准后单独重跑补充项。
